### Part A - recover the data (CAN decode)

Frame ID kept: `0x200` (`STEER_ActuatorLog`, decimal 512 in the DBC).

Signal 1 (u_commanded):  byte position / endianness / signed? / scale / offset:
`CmdAngularRate`: bytes 2-3 / little-endian / signed 16-bit / 0.1 / 0.
The decoded value is in deg/s.

Signal 2 (y_measured):   byte position / endianness / signed? / scale / offset:
`MeasuredAngle`: bytes 0-1 / little-endian / signed 16-bit / 0.1 / 0.
The decoded value is in degrees. Byte positions start at 0.

Notes (anything odd in the logs, how you checked the decode against the PNGs):

The logs also contain other CAN IDs, which we ignored. Each CSV starts at
the first kept frame's timestamp, with that time set to zero. There are
2,000 rows for `step_test`, 6,000 for `reversal_test`, and 4,000 for
`deadband_test`. The main shapes agree with the supplied PNGs: the step
settles near 56.1 deg, the reversal pauses at direction changes, and the
small-command test levels off near 2.6 deg.

I used the DBC to work out what the bytes in the log meant. For example,
`data/step_test.log` starts with:

`(1705638751.000000) vcan0 200#00009600D12FB01D`

The number in brackets is the timestamp, `vcan0` is the CAN interface, and
`200` is the frame ID in hexadecimal. The eight data bytes come after `#`.
To read the angle, I used this line from `SteeringBench.dbc`:

`SG_ MeasuredAngle : 0|16@1- (0.1,0) [0|0] "deg" Vector__XXX`

Breaking it down:

- `SG_` defines a signal, and `MeasuredAngle` is its name.
- `0|16` means start at bit 0 and read 16 bits, which covers bytes 0-1.
- `@1` means little-endian: the low byte comes first. `-` means signed,
  so the value can be negative.
- `(0.1,0)` means multiply the raw value by 0.1 and add no offset.
- `[0|0]` gives minimum/maximum information. Both are zero here, but the
  decoder does not use them to limit the angle.
- `"deg"` is the unit. `Vector__XXX` is a placeholder for the receiving node.

So in the first frame, `00 00` gives an angle of 0 deg. `CmdAngularRate`
uses bytes 2-3 with the same signed little-endian format and scale.
Those bytes are `96 00`, which gives 150 x 0.1 = 15 deg/s.

### Part B - identify system

For the gain, I used the steady part of `step_test.png`. The command is
15 deg/s, but the angle changes at about 19.5 deg/s, giving 19.5 / 15 = 1.3.
The angle also moves another 1.4 deg after the command stops. Dividing that
by 19.5 gives an estimated time constant of about 0.07 s.

The main clue for backlash was in `deadband_test.png`: the angle first
moves to about 2.6 deg, then stays there while the command keeps switching
between +2 and -2 deg/s. A simple deadzone would ignore small commands, but
these commands did move the output at first. `reversal_test.png` also shows
a pause when the direction changes. Backlash fits these observations because
the motor has to cross a gap before the output follows in the other direction.
We estimated about 5 deg across that gap, or a half-width of 2.5 deg.

In `plant.hpp`, we filled in `step()` with the speed lag, integrated motor
speed to get angle, and added the backlash gap. It matches these logs within
about 0.1 deg. I can only judge the model against the tests we were given.

### Part C - control design choices

The way I remember PID (proportional, integral and derivative) is that P
looks at the current error, I adds up past errors, and D looks at the trend.
The measured angle feeds back into the next command, which is how I started
to understand closed-loop control.

We used `kp = 2.5`, `ki = 0.08`, and `kd = 0.03`, with a command limit of
+/-15 deg/s. D uses changes in the measured angle, so changing the target
does not cause a sudden jump in this term. A 0.03 s filter smooths it because
the sensor readings come in 0.1 deg steps. We also limited the integral and
stopped it growing when it would push the command further past its limit.

Once the angle is within 0.1 deg of the target and nearly still, the
controller clears the integral and commands zero. This means accepting a small
error to avoid repeated tiny corrections. It only uses the target, measured angle,
and `dt`; it does not use the plant model while running.
